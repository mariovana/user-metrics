Problemas sistémicos de naming

⚠ convención

3 vocabularios de acción UI

37 eventos * Button Pressed, 20 * Clicked, 1 * Tapped — la misma semántica con tres nombres; imposible consultar "todos los taps" de forma genérica.

✕ typos

Typos con tráfico real

Viewed Bank Ticket Details (doble espacio) recibe 358,851/30d; Merge Account Iniciated 4,701; Viewed Credit Aplication Confirmation 4,604; Viewed Viewed Wallet Onborading.

⚠ idioma

Español e inglés mezclados

Viewed Tu negocio, Viewed Detalle de orden, Viewed Orden generada, Viewed Historial, Venta Exitosa conviven con el inglés dominante.

⚠ estilo

Casing sin regla

Title Case domina, pero hay sentence case (Payment calculator opened), snake (In_app Opened), minúsculas (created payment promise) y dot notation (Verification.Provider.Finished).

✕ ruido

Un dialer bombeando eventos

voicemail (883k), not_connected (671k) y connected (83k) — 1.6M eventos/30d de contact-center sin producto que contaminan "All Events".

ⓘ metadata

Metadata en el nombre

El paso (Onboarding 1/2/3), la secuencia (Loan 1 *), el vendor (Incode *) y el origen (Backend *, 28 eventos) van en el nombre en lugar de propiedades.

Hacia dónde converger

Propuesta v0 de taxonomía canónica (estándar Object + Action de Segment) y el plan para llegar sin romper dashboards. Detalle completo en docs/event-mapping.md.

Reglas de la taxonomía

  1. Nombre = Objeto + Acción en pasado, inglés, Title Case: Loan Application Submitted, Payment Completed.
  2. Una sola vista: Screen Viewed + prop screen_name — elimina 177 eventos (62% del volumen) de un plumazo.
  3. Una sola interacción genérica: Element Tapped + prop element_name; los hitos de negocio conservan evento propio.
  4. Resultados estándar: Started / Submitted / Completed / Failed — nunca Success, Successful, Succeeded y Approved para lo mismo.
  5. Props obligatorias: product, source, flow, step, provider — fuera del nombre.
  6. Mensajería consolidada: Message Sent/Opened/Clicked… + prop channel (email, push, in-app, webhook).
